# 구현 및 로컬 QA 결과

작성일: 2026-09-05
상태: 주요 기능 구현 및 로컬 QA 완료. 운영 DB 마이그레이션·GitHub push·Vercel 배포는 수행하지 않음.

## 유지한 운영 방식

링크를 전달받은 운영진이 이름을 입력하고 평가한다. 로그인이나 역할 분리를 추가하지 않았다. 아카이브 접근 범위, 서류 제출 후 타인 평가 공개, 서류·면접 점수 분리, Hermes 외부 생성, Drive 수동 보관을 유지했다.

## 구현한 변경

- 면접 메모·개인 평가를 독립적으로 저장한다. 저장 응답이 다른 미저장 입력이나 요청 중 추가 입력을 덮어쓰지 않는다.
- 공유 메모 버전 충돌 시 최신 메모를 보여주고 내 입력을 유지한다. 최신 내용을 확인한 뒤 다시 저장한다.
- 서류와 면접 평가를 DB 함수 한 번으로 저장한다. 항목·정수 점수·제출 완전성을 서버와 DB에서 검증하고, 실패 시 기존 평가를 보존한다. 제출 후 수정은 제출 상태를 유지한다.
- CSV 파일 선택 → 매핑 → DB 중복 비교 → 저장 → 목록 확인을 연결했다. 파일 내부 중복과 서로 다른 지원자를 가리키는 이메일/전화 충돌을 검사한다. 모집 단위 잠금과 트랜잭션으로 일괄 저장한다.
- 면접 목록에서 최종 미결정/합격/대기/탈락/보류를 저장하고 인원·목표를 확인한다. 결정 이력을 보관하고 오래된 버전의 변경은 거부한다.
- Hermes 입력 JSON/CSV 내보내기, 결과 예시와 미리보기, 오류 처리를 추가했다.
- ZIP에 명확한 범위 선택과 취소를 추가했다. 전체 종료본에는 최종 결정 이력, 개인정보 포함 선택 시 원본 보존 필드도 포함한다. 하위 조회 실패는 ZIP 성공으로 처리하지 않는다.
- 공통 메뉴, 평가자 설정 후 원래 화면 복귀, 서류 이전/다음 지원자 이동, 미저장 이탈 안내, 입력 label, 오류 재시도를 추가했다.
- 서류 목록은 지원자마다 순차 조회하던 방식을 일괄 조회로 변경했다.

통합 흐름은 가상 지원자 10명을 가져와 동일 파일 재비교, 답변 변경, 중복 오류, 서류 제출 및 블라인드 응답, 면접 지정·일정 배정, Hermes 내보내기/가져오기, 면접 제출, 최종 합격 저장, ZIP 3종의 실제 내용을 검사했다.

실제 PostgreSQL 엔진인 PGlite에서 마이그레이션과 DB 함수를 실행했다. 점수 삽입에 강제로 오류를 발생시켜 이전 점수 보존을 확인했고, 메모 충돌·최종 상태 충돌·잘못된 항목·소수 점수·CSV 전체 롤백을 검사했다. 익명 역할의 새 RPC 실행 권한이 없는 것도 확인했다.

UI 회귀 테스트는 응답을 지연시키거나 실패시켜 저장 중 추가 입력·다른 질문·개인 평가가 유지되는지 검사했다.

## 로컬 실행

저장소 루트 `source`에서 다음 명령을 사용한다.

```powershell
npm ci
# 터미널 1: 가상 데이터와 PostgreSQL API
npm run qa:db
# 터미널 2: QA 전용 환경변수로 Next.js 실행
npm run qa:app
```

브라우저: http://127.0.0.1:3000

QA 앱은 `127.0.0.1:54329`에만 연결하고 `local-qa-only`라는 테스트 키를 사용한다. 운영 Supabase 키가 필요하지 않으며 원격 DB에 테스트 데이터를 쓰지 않는다. QA DB는 메모리 기반으로 프로세스를 재시작하면 초기화된다.

```powershell
npm test
npm run typecheck
npm run lint
npm run build
# 새 QA DB를 시작한 뒤 실행
npm run qa:flow
```

이 PC에서는 `npm` 실행 경로에 문제가 있어 검증 때 npm CLI의 실제 경로를 사용했다. 위 npm 명령이 실패하면 다음과 같이 실행할 수 있다.

```powershell
node "C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js" run qa:db
node "C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js" run qa:app
```

## 배포 전에 남은 확인

1. `supabase/migrations/20260905041400_workflow_completion.sql`을 검토하고 대상 DB에 먼저 적용해야 한다. 새 화면의 저장 기능은 이 마이그레이션의 RPC·버전 열·결정 이력 테이블을 사용한다.
2. 운영 Vercel 환경변수와 실제 배포 커밋을 확인해야 한다. 기존 사이트의 ‘지원자 집계 조회 실패’의 정확한 운영 원인은 아직 확정하지 않았다. 원격 DB를 읽기 전용으로 확인한 결과 해당 모집·평가 항목은 존재하고 지원자와 면접 대상은 각각 0명이었다. 로컬 수정본의 조회는 정상이다.
3. 로컬 QA 서버는 필요한 PostgREST 동작 일부를 구현한 테스트 어댑터다. SQL은 실제 PostgreSQL에서 검증했지만 Supabase 전체 서비스, Vercel 런타임 및 운영 네트워크까지 검증한 것은 아니다. 배포 전 테스트 환경에서 실제 Supabase 연결 확인이 필요하다.
4. 현재 테스트 데이터는 소규모 모집 기준이다. Supabase 기본 조회 행 수 제한을 넘는 대규모 평가·아카이브의 별도 부하 검증은 하지 않았다.

운영 데이터와 기존 배포는 이번 작업으로 변경되지 않았다.
